问题（Question）

面试官最可能追问：“你说 harness 设计和训练数据设计有关，但工程 harness 到算法训练之间的过渡是什么？tool accuracy / scope correctness 这些指标为什么可以作为真实机器人任务控制能力的前置代理？”

短答案

可直接口述：harness 的价值不是“搭了平台”，而是把机器人集群控制中的可执行约束转成模型能学习、能被 reward 检查、能被 held-out 评估的 action/tool 语义。工程侧产生的是带上下文的任务状态、机器人状态、排他动作和取消补偿；算法侧消费的是 schema 化的 tool-call 样本、GRPO reward 和严格评估集。tool accuracy、scope correctness、critical-action correctness 不能证明真实机器人一定成功，但能证明模型在进入低层控制之前不会选错工具、越权操作、破坏时序约束，是真实任务执行能力的前置代理指标。

边界防线：不要说“tool accuracy 提升 = 机器人成功率提升”。更安全的表述是：它降低了无效/越权/时序错误的高层动作概率，为真实机器人闭环控制提供更干净的上层决策输入。

因果机制：工程 Harness 如何过渡到训练数据

可以把项目拆成三层：运行层、语义层、训练层。

层级输入设计动作输出面试时要强调
运行层 Harness 多会话任务、robot_id、robot memory、subagent、排他动作、取消请求、执行结果 定义任务状态机和 robot 级约束，记录“什么条件下允许做什么动作” 结构化 trace 和 action candidates 不是单纯并发调度，而是在抽象机器人控制语义
语义层 Schema trace、action、状态约束 把 action name、arguments、scope、precondition、cancelability、critical flag 写入 schema SFT 样本和 reward 可读字段 这是工程到算法的桥：约束从代码逻辑变成监督信号
训练层 SFT/GRPO 62,223 条 SFT 数据、8,916 条 GRPO 数据、held-out 评估集 SFT 学格式和基本动作分布，GRPO 用 schema-aware reward 约束工具选择、scope 和参数语义 32B holdout tool accuracy 95%+、coverage 约 96%、argument exact/semantic 92.3%/96.9% 指标是高层 action semantics 的代理，不是物理控制成功率

形式化地说，harness 产生的不是普通日志，而是带约束的训练样本：

\[ x = (c, m, s_r, q), \quad y = (tool, args, scope, temporal\_tag) \]

其中 \(c\) 是会话上下文，\(m\) 是 robot memory，\(s_r\) 是机器人状态，\(q\) 是用户或子任务请求；目标 \(y\) 是模型要输出的工具调用。实现映射上，harness 把原本散落在调度、互斥、取消补偿中的约束压成字段，训练时模型学习这些字段之间的对应关系。

def convert_trace_to_training_sample(trace):
    # 1. 从 harness trace 中读取用户意图、robot 状态和会话记忆。
    context = build_context(trace.session, trace.memory, trace.subagents)

    # 2. 将可执行动作规范化为 tool/action schema。
    schema = {
        "tool": trace.action.name,
        "args": normalize_args(trace.action.args),
        "robot_scope": trace.robot_id,
        "exclusive": trace.action.requires_mutex,
        "cancelable": trace.action.cancelable,
        "critical": trace.action.is_critical,
    }

    # 3. SFT 使用 schema 作为目标；GRPO 使用同一 schema 计算 reward。
    return {"prompt": context, "target": schema}

哪些约束进 Schema，哪些进 Reward，哪些进 Holdout Eval

约束类型进入 Schema进入 Reward进入 Holdout Eval为什么这样放
工具选择 tool name、动作类别、critical flag tool exact match / semantic match tool accuracy 高层动作选错会直接导致任务无效，是第一优先级
参数约束 参数字段、类型、必填项、可选项 argument exact / semantic reward argument exact / semantic match 参数是工具调用能否落到正确对象或状态的关键
robot scope robot_id、multi-robot boundary scope correctness reward scope correctness 避免跨 robot 越权、抢占或串会话
排他动作 exclusive / mutex 标记 非法并发惩罚 critical case set 导航、抓取、下单等长时序动作不能被中间状态抢占
取消补偿 cancelable、cancel target、compensation action 取消顺序和目标一致性 reward cancel scenario holdout 真实系统里取消比正常执行更容易暴露语义漏洞

GRPO reward 可以用分项组合解释：

\[ R(y,\hat{y}) = w_t r_{tool} + w_a r_{arg} + w_s r_{scope} + w_c r_{critical} - w_v r_{violation} \]

这里 \(\hat{y}\) 是模型输出，\(y\) 是 schema 目标；\(r_{tool}\) 约束工具选择，\(r_{arg}\) 约束参数，\(r_{scope}\) 约束 robot 归属，\(r_{critical}\) 约束关键动作，\(r_{violation}\) 惩罚非法并发或取消错误。面试中不必强调具体权重，而要强调 reward 不是泛泛打分，而是由 harness 暴露出来的可执行约束组成。

4. 2-3 分钟口述稿

这个项目的背景是机器人平台里存在多会话、多机器人和长时序动作，单纯把工具接起来并不能保证模型输出可执行。我的工作是把平台控制约束抽象为 robot task harness 和统一 task/action schema。具体来说，我把 robot memory、subagent 分工、robot scope、排他动作、取消补偿这些约束显式进入 schema，再把 schema 转成 SFT 数据和 GRPO reward。这样工程侧的“什么动作在什么状态下可执行”，就变成模型侧可学习、可评估的监督信号。结果上，我们构建了 62,223 条 SFT 和 8,916 条 GRPO 数据，主线扩展到 Qwen3-VL-32B，holdout tool accuracy 从 base 的 37.8% 提升到 95% 以上，coverage 约 96%，严格集中工具选择、robot scope 和 critical action 都达到 100%。这个结果的边界是，它证明的是高层工具调用语义，不等价于真实机器人成功率；但它是进入真实控制闭环前非常关键的前置代理，因为低层控制再强，也承受不了上层工具选错、越权或破坏时序。

追问树

面试官问题危险回答可过回答强回答策略
“这不就是工程链路吗，算法价值在哪里？” 我搭了 harness，然后拿数据训练。 harness 产出了结构化训练样本。 把工程约束转成可学习语义：schema 定义监督空间，reward 定义优化目标，holdout eval 定义泛化检查。
“tool accuracy 为什么能代表机器人能力？” 工具调用准确，机器人就能执行。 它是高层决策正确性的代理。 它是必要非充分条件：只能证明上层动作语义、scope 和参数约束，不能覆盖视觉、控制延迟、物理接触。
“你怎么防止 reward hacking？” reward 规则比较严格。 我们用 held-out 做验证。 reward 分项和 holdout 分项解耦：训练时看 tool/arg/scope，评估中增加 critical/cancel 场景，避免只学格式。

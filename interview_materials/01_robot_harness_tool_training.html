问题（Question）

面试官最可能追问：“你说 harness 设计和训练数据设计有关，但工程 harness 到算法训练之间的过渡是什么？tool accuracy / scope correctness 这些指标为什么可以作为真实机器人任务控制能力的前置代理？”

短答案

可直接口述：这是我以 owner 方式完整推进的项目，工程实现和 schema 字段展开主要由 Codex 完成；我负责把机器人集群控制里的上层失败模式定义成可训练问题，包括任务目标、工具协议约束、数据分流策略、训练口径、D/OOD eval 和验收指标。harness 的价值不是“搭了平台”，而是先把工具选择、参数格式、robot scope 这类高层动作语义稳定下来，尤其是导航参数写错这种会直接导致任务失效的问题。训练数据主体来自开源工具调用/Agent 数据，一部分内部通用数据用于补通用能力，少量业务数据主要进入 eval。实际脚本里，SFT 走 OpenAI-compatible messages + tools 的 teacher-forcing 路径：排除 ToolACE，保留可清洗的工具调用样本、project sandbox 轨迹样本和少量高层 VQA 辅助；GRPO 走 rewardable RL task 路径：从 allowed/forbidden tools、reference trajectory、success criteria、policy constraints、minefields 等字段构造可规则判分任务，并在 32B 阶段额外加入 tool-restraint no-call/clarification mix。tool accuracy、scope correctness 和 argument correctness 不能证明真实机器人一定成功，但能证明模型在进入低层控制前不会频繁选错工具或写错关键参数，是真实任务执行能力的前置代理指标。

边界防线：不要说“tool accuracy 提升 = 机器人成功率提升”。更安全的表述是：它降低了无效工具、错误参数、越权 scope 等高层动作错误概率，为真实机器人闭环控制提供更干净的上层决策输入。memory/subagent 是 harness 的 runtime 抽象，目前没有足够训练数据支撑它们作为模型训练主线。

Research Framing：把经历讲成研究问题

面试时可以把这个项目拆成三个研究阶段，而不是只讲“做了 harness + 训练”。每个阶段都按 Motivation / Hypothesis / Method / Experiment / Failure Analysis 展开。

阶段Motivation 动机Hypothesis 假设Method 方法Experiment 实验Failure Analysis 失败分析
1. Robot harness 语义抽象 机器人集群控制不是普通 function calling：同一 robot 的排他动作、取消补偿、会话状态、robot scope 都会影响真实执行。对应论文更多是 embodied agents / tool use / function calling 的方法背景，不是某篇论文的直接复现；开放问题是如何把高层语言指令转成安全、可执行、可追踪的 robot action semantics。 真实任务失败中有一类不是视觉或低层控制失败，而是上层工具协议错误：工具选错、导航参数写错、robot_id/scope 错。只要先降低这些高层错误，就能为后续真实控制提供更干净的输入。 设计 harness 作为语义边界：任务上下文、robot 状态 memory、subagent 分工、排他动作、取消补偿和工具协议统一进入 action/tool schema；工程实现和字段展开主要由 Codex 完成，我负责约束定义、取舍和验收。 通过 runtime trace、schema 样本和 holdout case 检查输出是否可解析、scope 是否正确、导航参数是否合规。这里的实验不是物理任务成功率，而是工具协议层的可执行性验证。 memory/subagent 当前更多是 runtime 抽象，训练数据覆盖不足；不能把它们说成模型已经学会的能力。面试防线是：训练主线先收敛到工具协议、参数和 scope。
2. SFT / GRPO 数据设计 开放问题是：结构化工具调用能力能否作为真实机器人任务控制的前置代理？对应方法背景是 schema following、tool learning、RL with verifiable rewards；本项目不是泛泛做 post-training，而是把机器人控制约束转成可监督、可 reward 的样本。 SFT 更适合学习稳定协议格式、工具调用模板和语言/通用能力；GRPO 更适合承载可规则判分的行为约束，例如 forbidden tool、clarification、scope、cancel/compensation 和参考轨迹。这样比把所有样本平均 SFT 更能处理“导航参数错、scope 越权、格式违规”这类致命错误。 脚本上分成两条路径：SFT 从 openai_tool_sft.jsonl、project sandbox 与高层 VQA auxiliary 构造 teacher-forcing 样本；GRPO 从 rl_tasks_train_ready.jsonl 和 project sandbox 轨迹构造 rewardable task，并在 32B 训练阶段加入 tool-restraint no-call/clarification mix。 v2 manifest 记录 62,223 条 SFT 数据与 8,916 条 canonical GRPO 数据；32B GRPO train mix 在 8,052 条 train 上额外合成 1,200 条 tool-restraint 样本。主线扩展到 32B 后，tool-call holdout 的 tool accuracy 从 37.8% 提升到 95% 左右，robot sandbox 的 argument exact/semantic match 达到 92.3%/96.9%。 这些指标只能证明高层工具协议能力，不等价于真实机器人成功率。下一步要补 SFT-only / no-scope-reward / no-arg-reward ablation，并接小型闭环仿真或真实机器人任务。
3. D/OOD eval 与代理指标 研究动机是避免“训练 loss 降了但任务不可用”。机器人控制前置能力需要可解释评估：in-domain 工具协议、业务分布样本、OOD safety/general suite 分开看。 如果 tool accuracy、scope correctness、argument correctness 在 held-out 上稳定提升，说明模型至少减少了进入控制器前的高层动作错误；但视觉、控制延迟、物理接触仍需独立评估。 提前切出 D split，OOD 引入安全/通用能力 suite；业务数据规模小，因此主要用于 eval，而非训练主干。评估拆成 tool、arg、scope、coverage 和格式合规。 用 holdout 指标证明协议能力提升，并通过 robot sandbox 样本检查工具/参数/scope 是否稳定。面试里强调这是“前置代理指标”，不是最终任务成功率。 最大失败风险是评估泄漏和 proxy overclaim。防线：不把 tool-call 指标写成真实机器人成功率；补证据方向是固定 split manifest、bad-case gallery 和闭环任务验证。

Grill Me 预留问题：如果后续要再精确，你需要补一张表：每类工具协议错误在训练前后的占比、真实 robot trace 中这些错误对应的任务失败例子、以及 32B SFT-only vs SFT+GRPO 的差分。

因果机制：工程 Harness 如何过渡到训练数据

可以把项目拆成三层：运行层、语义层、训练层。

层级输入设计动作输出面试时要强调

形式化地说，harness 产生的不是普通日志，而是带约束的训练样本：

\[ x = (c, q, d), \quad y = (tool, args, scope) \]

其中 \(c\) 是多轮上下文，\(q\) 是用户或子任务请求，\(d\) 是工具定义和协议描述；目标 \(y\) 是模型要输出的工具调用。实现映射上，harness 的工程代码与多数 schema 字段由 Codex 生成，但训练数据的关键不是代码本身，而是样本是否严格遵守我定义的 harness 约束与验收口径，尤其是工具名、导航参数和 robot scope。

def route_sample(sample):
    # SFT: clean teacher-forcing data in OpenAI-compatible messages + tools.
    if sample.file == "openai_tool_sft.jsonl" and sample.source != "ToolACE":
        return "sft", normalize_messages_and_tool_calls(sample)

    # SFT + GRPO: project sandbox rows are useful only when they have expected trajectory.
    if sample.file == "agent_sandbox_cases_project_ready.jsonl" and sample.expected.trajectory:
        return ["sft", "grpo"], build_project_protocol_row(sample)

    # SFT auxiliary: high-level VQA/general capability; exclude coordinate, bbox, point, and action-token targets.
    if sample.is_point_general_vqa and not sample.has_low_level_coordinate_or_action_target:
        return "sft_aux", build_language_or_vlm_auxiliary_row(sample)

    # GRPO: rewardable RL task rows with tools, constraints, trajectories, minefields, or clarification targets.
    if sample.file == "rl_tasks_train_ready.jsonl":
        return "grpo", build_rewardable_task(sample)

    # 32B GRPO train mix: tools are visible, but correct behavior is no tool call plus clarification/refusal.
    if sample.is_tool_restraint_candidate and sample.source != "AppWorld":
        return "grpo_train_mix", synthesize_tool_restraint_row(sample)

    return "eval_or_drop", keep_only_if_useful_for_holdout(sample)

样本分流证据：哪些进 SFT，哪些进 GRPO

这部分是本轮补强后的核心证据。面试里不要只说“可 reward 的进 GRPO，剩下进 SFT”，而要能落到脚本条件、字段和训练目的。

样本类型进入路径脚本条件 / 字段训练目的面试边界
OpenAI-compatible 工具调用样本 SFT prepare_sft_data.py 读取 openai_tool_sft.jsonl，显式排除 source == "ToolACE"；规范化 messages、tools、assistant tool_calls 与 JSON-string arguments。 学习工具调用格式、工具名、参数结构和稳定输出协议，是 teacher-forcing 的主干。 这是协议 imitation，不是 RL；不要把它讲成 reward 优化。
Project sandbox / robot 轨迹样本 SFT + GRPO SFT 路径读取 agent_sandbox_cases_project_ready.jsonl；GRPO 路径只保留 expected.trajectory 非空样本，并写入 reference_trajectory、success_criteria、scope_id/scope_type、allowed_tools、forbidden_tools。 SFT 学协议目标，GRPO 用轨迹、状态检查、scope 与 forbidden tools 做规则 reward。 memory/subagent 是 harness runtime 抽象；训练主线不是“训练 memory/subagent”，而是工具协议、参数和 robot scope。
Robo2VLM / point-general 高层 VQA 辅助 SFT auxiliary keep_point_general 排除 RoboPoint、<point>/<box>、coordinate/bbox prompt、低层 action-token target；v2 language-only 脚本移除图像输入并保留文本提示/答案。 保留通用语言/视觉语义能力，避免纯工具协议训练过窄。 它不是 robot tool reward 数据，也不用于证明真实机器人执行能力。
RL train-ready 工具任务 GRPO canonical prepare_grpo_data.py 读取 rl_tasks_train_ready.jsonl，保留 allowed_tools、forbidden_tools、reference_trajectory、success_criteria、policy_constraints、minefields；WebLINX/Mind2Web browser runner 默认不进 GRPO。 把工具顺序、参数语义、禁止副作用、澄清请求、scope 边界和状态成功转成 reward。 GRPO 的价值在规则可判分；没有可靠 reference/reward 的样本不应硬塞进 RL。
Clarification / refusal / no-action 工具克制样本 32B GRPO train mix build_grpo_tool_restraint_mix.py 合成“工具可见但正确行为是不调用工具、转而澄清或拒绝”的样本；AppWorld quarantine 被排除，因为空轨迹常表示缺 runner trajectory，不等价于真实 no-action label。 补足“有工具也不能乱调”的克制能力，约束 forbidden side effect 和 missing-info 情况。 这是 train-only mix：原 canonical GRPO 总量仍是 8,916；32B 混合 train 是 8,052 + 1,200 = 9,252。
OOD / safety / general probe 与少量业务样本 Eval / OOD probe OOD suite 与少量业务分布样本主要用于验收；用户口径是业务数据百条级，更多进入 eval 而非 train。当前未看到独立“大规模业务 train split”脚本证据。 检查协议能力是否泛化到真实业务分布、安全/通用能力和 schema-absent 情况。 这是面试防线：不能暗示有大量业务数据训练，也不能用 OOD probe 的混合结果包装成全面提升。

GRPO reward 可以用分项组合解释：

\[ R(y,\hat{y}) = w_t r_{tool} + w_a r_{arg} + w_s r_{scope} + w_f r_{format} - w_v r_{violation} \]

这里 \(\hat{y}\) 是模型输出，\(y\) 是 schema 目标；\(r_{tool}\) 约束工具选择，\(r_{arg}\) 约束参数，\(r_{scope}\) 约束 robot 归属，\(r_{format}\) 约束工具协议格式，\(r_{violation}\) 惩罚违反协议的输出。面试中不必强调具体权重，而要强调 reward 不是泛泛打分，而是围绕 harness 期望的工具协议，尤其是导航参数和 scope 正确性。

4. 2-3 分钟口述稿

这个项目是我以 owner 方式推进的工具调用训练项目，工程实现和 schema 字段展开主要由 Codex 完成，我负责的是问题定义、harness 约束、数据分流、训练/eval 口径和指标验收。背景是机器人任务控制里，很多失败不是低层控制问题，而是上层工具协议错误，比如导航参数写错、scope 写错、工具选择错误。我的做法是先用 harness 明确机器人集群控制的 runtime 抽象，再把最适合训练的部分收敛到工具协议、参数和 scope：SFT 侧保留 OpenAI-compatible tool-call、project sandbox 轨迹样本和少量高层 VQA 辅助，用来学习稳定格式和工具协议；GRPO 侧只放具备 reference trajectory、allowed/forbidden tools、success criteria、policy constraints 或 minefields 的可判分样本，并在 32B 阶段补 tool-restraint 样本，让模型学会“有工具也不能乱调”。数据来源上，主体来自开源数据集，一部分内部通用数据补通用能力，少量业务数据主要进入 eval。结果上，我们构建了 62,223 条 SFT 和 8,916 条 canonical GRPO 数据，主线扩展到 Qwen3-VL-32B，在同一 holdout 口径下 tool accuracy 从 37.8% 提升到 95% 以上；robot sandbox 上 tool/coverage/critical/scope 达到 100%，GRPO 后 argument exact/semantic match 达到 92.3%/96.9%。这个结果的边界是，它证明的是高层工具调用语义和参数正确性，不等价于真实机器人成功率；但它能显著降低真实控制前最致命的协议错误。

6. 高频追问

追问推荐答法防线 / 证据
harness 和训练数据之间的中间产物是什么？中间产物是可执行的 tool/action schema、带字段校验的样本、rewardable 标签和 holdout case。harness 先定义机器人集群控制里什么叫合法动作，训练数据再把这些合法动作转成 SFT 监督和 GRPO reward。不要说 harness 自动生成能力；证据是 schema、样本路由规则和 SFT/GRPO 数据统计。
哪些 harness 约束被转成了 schema 字段、reward 项和 holdout 指标？schema 放工具名、参数类型、robot_id/scope、可取消动作等硬约束；reward 检查工具选择、导航参数、scope 越权和格式违规；holdout 评估 tool accuracy、argument correctness、scope correctness 和 OOD 安全/通用能力。schema、reward、eval 要分层讲；不要混成“都做了评测”。
为什么 tool accuracy 可以作为代理指标？它是上层动作语义的前置代理。真实机器人失败可能来自视觉或控制，但如果上层已经选错工具、写错导航参数或发给错误 robot，低层控制无法弥补。必要非充分条件；不能说 tool accuracy 等于真实成功率。
这个代理指标有哪些盲区？它不覆盖视觉 grounding、路径规划、控制延迟、物理接触、执行器异常和长时序恢复。它只证明进入控制器前的工具协议更干净。主动承认盲区比硬辩更强；后续要补闭环仿真/真实机器人验证。
到底哪些样本进 SFT，哪些样本进 GRPO？SFT 进的是可规范化成 OpenAI-compatible messages + tools 的 teacher-forcing 样本，包括主工具调用、project sandbox 轨迹样本和少量高层 VQA auxiliary；ToolACE 在 SFT 脚本中被排除。GRPO 进的是 rl_tasks_train_ready 里带 allowed/forbidden tools、reference trajectory、success criteria、policy constraints、minefields 等字段的可判分样本，以及有 expected trajectory 的 project sandbox 样本；32B 阶段再加 tool-restraint no-call/clarification mix。证据是 prepare_sft_data.py、prepare_grpo_data.py、build_grpo_tool_restraint_mix.py 和 manifest。
SFT 和 GRPO 各自解决什么问题？SFT 负责把工具协议、格式和参数习惯稳定学进去，是 imitation；GRPO 负责强化可规则判分的行为约束，包括工具顺序、参数语义、scope、forbidden side effect、clarification、cancel/compensation 和 tool restraint。不要把 SFT/GRPO 讲成泛泛“训一训”；要绑定脚本字段和 reward 条件。
reward 是规则写死的吗，还是模型打分？主线是 schema-aware 规则 reward，不依赖另一个模型主观打分。它围绕工具名、参数、scope、格式和致命错误惩罚构造，优点是可复现、可解释，缺点是覆盖不到所有语义细节。证据是 reward checker；不要声称 reward 能评估真实执行质量。
训练里哪些字段真的有数据支撑？训练主线有数据支撑的是工具协议、工具选择、导航参数、robot scope、参数格式和部分安全/通用能力。memory/subagent 更多是 runtime 抽象，当前不是训练主线。这是高危边界题；不要把 harness 中所有抽象都说成已训练。
scope correctness 错了会发生什么？scope 错会把动作发给错误 robot，或让一个会话越权影响另一个 robot 的活跃请求。在集群控制里这比普通格式错误更严重，因为会造成物理执行对象错误。可结合 robot_id、互斥动作、取消补偿来解释。
memory/subagent 为什么没有作为训练主线？因为缺少足够覆盖的训练样本，强行写成训练能力会越界。它们更适合作为 harness runtime 功能，当前训练优先解决工具协议和导航参数这些更致命的错误。防线：runtime 有，训练主线没有充分覆盖。
少量业务数据为什么主要放 eval？业务数据只有百条级，作为训练主干会过拟合且难以证明泛化；放进 eval 更有价值，用来检查开源/通用数据训练出的协议能力是否覆盖真实业务分布。不要暗示有大规模业务训练数据；强调泄漏控制。
8B 和 32B 的定位有什么不同？8B 是 reward 和样本口径 pilot，用来快速验证协议和暴露错误；32B 是主线容量，能更接近实际部署。面试里要把指标重点放在 32B holdout 的工具协议提升上。不要把 8B 包装成主成果，也不要错误比较协议不同的 base。
为什么不直接让模型学自然语言轨迹？自然语言轨迹可读但不可稳定执行，缺少类型、scope 和参数约束。机器人控制需要模型输出能被 harness 验证和执行的结构化动作，否则评估和失败归因都不稳定。核心是可执行性、可评估性、可归因性。
如何构造 held-out，避免和训练集泄漏？脚本使用 stable hash 按 normalized goal + expected/reference trajectory 做 group-level split，WebLINX/Mind2Web 按 demo/task id，ARL-SCOUT 按 transcript/trial id，避免同一轨迹变体同时出现在 train/test；OOD suite 独立作为压力测试。证据是 manifest 的 split rule；不要用训练后 bad case 反复调到 holdout 上。
coverage 约 96% 指什么？coverage 指模型在 holdout 中能输出可解析、可进入评测的工具调用比例。它和 accuracy 不同：coverage 低说明格式或拒答问题，accuracy 高但 coverage 低也不能算可用。把 coverage 与 tool accuracy 区分开。
argument semantic match 怎么判断？exact match 看参数字符串或结构完全一致；semantic match 允许同义表达、可等价解析的参数或轻微格式差异。机器人场景中导航目标、位置描述和对象名更适合同时看 exact 与 semantic。必须说明人工/规则口径；不要让 semantic match 变成主观放水。
如果真实机器人执行失败，如何判断是工具层还是控制层问题？先看模型输出：工具名、参数、scope、格式是否正确；再看 harness 调度和取消互斥；最后看导航、视觉和控制器日志。如果工具层正确但执行失败，就不能用 tool accuracy 解释，需要进入低层控制诊断。分层 trace 是关键证据。
这个设计和普通 function calling 有什么区别？普通 function calling 更多是软件 API 参数约束；这里面向机器人集群控制，多了 robot scope、排他动作、取消补偿、长时序任务和物理执行风险。因此 schema/reward 不只是格式，而是控制安全边界。避免说“更高级”；具体说多了哪些机器人约束。
如果工具 schema 变更，训练数据如何更新？先做 schema versioning 和迁移脚本，把旧样本解析到新字段；不能迁移的样本降权或剔除；reward checker 和 holdout 同步版本化，避免模型按旧协议训练、新协议评测。可补证据：schema diff、数据迁移日志、回归评测。
工程实现由 Codex 完成，你个人贡献在哪里？Codex 是实现加速器。我负责定义问题、拆机器人集群控制约束、决定数据分流和 reward/eval 口径、判断结果和 bad case；Codex 把这些约束落成代码和 schema。不要说自己手写所有工程；也不要把自己降成“只让 Codex 写”。
如果继续做，下一步补什么证据？最优先补闭环验证和 ablation：无 scope reward、无参数 reward、SFT-only 对比，以及小型仿真/真实机器人任务成功率。这样能把 tool-call proxy 和真实执行之间的证据 gap 缩小。补证据方向要服务因果解释，不是多跑几个日志。

Grill Me：高压追问答复卡

高压追问推荐口述危险边界需要证据
“harness 设计”和“训练数据设计”之间到底有什么因果关系？ harness 不是训练后的附属平台，而是先定义机器人集群控制里什么叫合法的高层动作：工具名、参数、robot scope、可取消时序和互斥动作。训练数据再按这些约束被清洗成模型要学习的 action/tool 语义：SFT 路径承载可规范化的 teacher-forcing 协议样本，GRPO 路径承载具备 reference trajectory、forbidden/allowed tools、success criteria、policy constraints、minefields 或 tool-restraint 目标的可判分样本。所以因果关系是：harness 定义可执行语义和失败边界，数据设计把这些语义转成监督目标、reward 项和 holdout 指标。 不能说 harness 自动产生机器人能力，也不能说 tool-call 指标等价于真实任务成功率。 schema 字段、数据路由规则、SFT/GRPO 样本统计、D/OOD holdout。
哪些约束进 schema，哪些进 reward，哪些进 holdout eval？ schema 放“必须结构化且执行前可解析”的约束，例如工具名、参数类型、robot_id/scope、可取消动作字段；reward 放“可以用规则判定对错”的行为约束，例如工具选择、导航参数合法性、scope 越权和格式违规；holdout eval 则放最终验收问题，包括 in-domain 工具协议、OOD 安全/通用 suite，以及少量业务分布样本。 不要把 schema、reward、eval 混成一件事；schema 是输出契约，reward 是训练信号，eval 是验收协议。 reward checker、holdout 划分说明、OOD suite 列表。
tool accuracy / scope correctness 为什么可以当真实机器人能力的前置代理？ 它们不是充分条件，但是真实执行前的必要条件。机器人失败有很多低层原因，但如果上层已经选错工具、写错导航参数或把动作发给错误 robot，低层控制再强也救不回来。所以这些指标衡量的是进入控制器前的高层动作合法性。 不能说“工具调用准，所以机器人一定成功”。要主动补一句还缺视觉、控制延迟、物理接触和闭环恢复验证。 tool/arg/scope 指标、导航参数 bad case、真实/仿真闭环计划。
8B 和 32B 怎么讲，哪个是主线？ 8B 更像 reward 口径和样本协议的 pilot，用来快速暴露 schema、导航参数和 holdout 设计的问题；主线价值在 32B，因为它更接近实际部署模型容量。面试里我会说：在同一工具协议 holdout 上，32B 经过 SFT/GRPO 后工具选择和参数合法性稳定到 95% 左右，说明协议监督能迁移到更大模型，而不是只在 toy 8B 上成立。 不要把 base 8B 的协议不兼容说成“0% 能力”，也不要把 8B pilot 包装成主成果。 32B holdout 表、SFT/GRPO 对照、协议版本说明。
memory / subagent / 任务并行有没有进入训练？ 它们主要是 harness runtime 抽象，用来服务机器人集群控制：状态 memory、subagent 分工、排他动作、取消补偿和不同机器人并行。当前训练主线不是让模型学习 memory/subagent，而是先解决工具协议、导航参数和 robot scope 这些更致命的动作合法性问题。 不能说 memory/subagent 已经被 SFT/GRPO 充分训练；这会被追问数据来源。 harness 设计文档、runtime trace、训练样本字段覆盖统计。
业务数据只有百条左右，为什么项目还有价值？ 业务数据太少，不适合作为训练主干。我的处理是让开源/通用数据承担主体训练，内部通用数据补通用能力，少量业务样本更适合提前从训练中隔离出来做 eval，检查模型是否能在真实业务分布和安全约束下遵守工具协议。 不要暗示大规模业务数据参与训练，也不要用业务数据支撑泛化结论。 数据来源分布、业务样本 eval 划分、泄漏控制说明。
工程实现全由 Codex 完成，你个人贡献怎么讲？ 我会把 Codex 讲成实现加速器，而不是个人贡献替代品。我的贡献在问题定义、机器人集群控制需求拆解、工具协议和数据分流策略、reward/eval 口径、训练结果判断和 bad case 归因；Codex 负责把这些约束快速落成 schema、harness 和脚本。面试里重点讲我如何决定“什么要学、怎么验收、哪里算失败”。 不要说自己手写了所有工程实现；也不要把贡献降成“让 Codex 写代码”。 设计记录、prompt/PR 历史、数据与评估产物、结果复盘。
如果真实机器人任务失败，怎么判断是工具协议问题还是低层控制问题？ 先分层定位：第一层看模型是否选对工具、参数和 scope；第二层看 harness 是否正确调度、取消和互斥；第三层看导航/控制器输入是否合理；最后看视觉定位、控制延迟和物理接触。如果第一层错，回到 schema/reward 和数据；如果第一层对但执行失败，就不能再用 tool accuracy 解释，需要补闭环控制和环境分布诊断。 不要把所有失败都归因到模型，也不要把低层控制失败写成训练成功。 分层 trace、失败样例、工具输出和执行日志对齐。

FAST（上游对照）：连续动作与 token 的互转机制

本节讲的是 Physical Intelligence 的公开 FAST 机制，不是当前 Qwen formal trainer 的实现证明。当前 local route 的代码路径是 assistant-side JSON + causal LM CE；除非补到 FAST processor 调用和 roundtrip test，否则两者必须分开表述。

FAST 的全称是 Frequency-space Action Sequence Tokenization。它解决的问题是：VLA 自回归模型天然预测离散 token，而机器人控制需要连续 action。FAST 不是逐维逐时刻做 naive binning，而是把一段动作序列看成可压缩的时间信号。

令动作维度为 \(d\)，horizon 为 \(H\)，一个 action chunk 为：

\[ A_{t:t+H-1} = [a_t, a_{t+1}, \ldots, a_{t+H-1}], \quad a_t \in \mathbb{R}^{d} \]

FAST 路径可以概括为：

\[ A \xrightarrow{\mathrm{normalize}} \tilde{A} \xrightarrow{\mathrm{DCT}} C \xrightarrow{\mathrm{quantize/BPE}} z \xrightarrow{\mathrm{decode}} \hat{C} \xrightarrow{\mathrm{IDCT}} \hat{A} \]

其中 \(A\) 是连续 action window，\(\tilde{A}\) 是归一化后的动作，\(C\) 是 DCT 频域系数，\(z\) 是模型可生成的 token 序列，\(\hat{A}\) 是最终还原给 controller 的动作窗口。项目里你提到的 encode / dct / idct / decode 正是这个思路：encode 阶段把连续动作压成 token，decode 阶段把 token 还原为动作。

面试点专业回答简化回答
为什么 DCT？ DCT 把时间域动作分解成低频/高频系数。机器人轨迹通常有较强时序平滑性，低频系数承载主要趋势，压缩后 token 更短、更适合自回归预测。 不是逐帧猜动作，而是先用频域把一段动作压成更短的“动作句子”。
会不会损失精度？ 会有量化和截断误差。误差来自 normalizer、DCT 系数保留/量化、BPE token 有效性和 decode 失败兜底；不能说无损，只能说在闭环 replanning 下可控。 有损，但不是一次预测完整任务；每次只执行 action chunk 的前几步，再重新看图规划。
和 JSON action token 的关系 FAST 是上游频域 action tokenizer；我本地复现路径为了 Qwen3-VL LoRA 训练可执行，把 action horizon 序列格式化成 assistant-side action JSON / token 监督，这是一条迁移复现口径，不等同于原 action expert 的完整等价复刻。 我做的是让 Qwen 路线稳定读写动作格式，保证输出最终能回到 controller 可执行的连续动作。

Action Window、Normalization 与 Controller 闭环

camera / state / task language
        |
        v
OpenPI / Qwen policy path predicts action token or action chunk
        |
        v
decode -> normalized continuous action window
        |
        v
denormalize / slice / map to environment controller action
        |
        v
execute first K actions, then re-observe and replan

闭环控制的关键变量是 \(H\) 和 \(K\)：\(H\) 是一次预测的未来动作长度，\(K\) 是实际执行多少步后重新规划。

\[ \pi_\theta(o_t, s_t, c) \rightarrow \hat{A}_{t:t+H-1}, \quad env.step(\hat{a}_t), \ldots, env.step(\hat{a}_{t+K-1}) \]

\(H\) 太短，模型难以表达跨阶段动作意图；\(H\) 太长，后半段动作容易因为新观测变化而过时。\(K\) 越小，闭环更稳但推理成本更高；\(K\) 越大，执行更流畅但更依赖 open-loop 预测。面试里要讲这个 trade-off，而不是只背 horizon 数字。

def rollout_with_action_chunk(env, policy, task, replan_steps):
    # 1. Reset simulator and read image/state observations.
    obs = env.reset(task)
    done = False
    while not done:
        # 2. Build model input with the same observation normalization as training/eval.
        model_input = build_policy_observation(obs, task)

        # 3. Query policy and parse predicted tokens/chunk into continuous actions.
        pred = policy.infer(model_input)
        action_window = decode_denormalize_and_slice(pred)

        # 4. Execute only the first K actions, then observe again.
        for action in action_window[:replan_steps]:
            obs, reward, done, info = env.step(action)
            if done or info.get("success"):
                break
    return info

5. 高频追问答复

追问推荐答法防线 / 证据
FAST 的核心思想是什么？FAST 是 Frequency-space Action Sequence Tokenization，把连续 action window 先归一化，再用 DCT 转到频域，量化/BPE 成 token；推理时再 decode、IDCT、反归一化回连续动作。FAST/OpenPI 不是个人原创；引用上游论文和 tokenizer。
连续动作 token 化为什么不是纯离散化玩具？因为 token 表示的是一段频域动作序列，不是把每个动作维度粗暴编号。它保留了时间相关性，让 VLA 能用序列预测学习 action chunk。承认有量化误差；靠闭环 replanning 缓解。
DCT/IDCT 在这里解决什么？DCT 把时间序列压成频域系数，低频部分表达平滑动作趋势，高频表达细节；IDCT 再还原连续动作。它让动作序列更容易被压缩和 token 化。不要说无损；截断和量化会损失细节。
action window 和 execution window 有什么区别？action window 是模型一次预测的未来动作段，execution window 是控制器实际执行多少步后重新观测。前者影响规划跨度，后者影响闭环纠偏频率。要讲 trade-off，不只背 horizon 数字。
horizon 太长或太短会怎样？太短看不到跨阶段意图，太长后半段容易因新观测变化而过时。真实控制里常需要在规划长度和闭环频率之间折中。证据可来自不同任务失败视频或配置对比。
normalization 为什么关键？动作各维尺度不同，不归一化会让某些维度主导 loss；反归一化错会导致执行过冲、夹爪错误或动作幅度不足。normalizer 是训练和 eval 可比的关键 contract。不要把 normalizer 当普通配置项。
controller 执行和模型输出之间怎么闭环？模型输出 action chunk，经 decode/denorm 后交给 controller 执行一小段；环境产生新观测后再进入下一轮预测。闭环关键是重新观测和重新规划。格式正确不等于控制正确；要看执行轨迹。
Qwen 接入不就是换 backbone 吗？不只是换名。要处理视觉输入、chat template、assistant-side action 监督、LoRA target、loss mask、保存加载和 eval 输出解析，让 Qwen3-VL 能承担 VLA/VLM/co-train 三条路径。不要声称改了原始 action expert 核心结构。
assistant-side action JSON/token 为什么合理？它是 Metax 复现路线的可执行折中，使 DROID action 和 MindCube QA 能进入同一 Qwen causal LM 训练。它用于复原训练语义，不宣称完全等价于上游 action expert。边界要清楚：工程折中，不是 SOTA 新方法。
三条训练路径分别是什么？DROID VLA-only 关注动作监督，MindCube VLM-only 保留视觉语言问答能力，DROID+MindCube co-train 验证动作和 VLM 任务能否在统一 Qwen 训练口径下共存。证据是 recipe、run contract 和训练脚本。
动作统一具体统一了什么？统一输入输出 contract：动作维度、序列长度、normalizer、assistant 输出格式、loss mask 和 eval 解析方式。这样训练和 rollout 不会各用一套动作语义。不要只说“格式统一”；要讲 contract。
224_h10_40000 是什么？它是 committed formal report 里的归档 run 标签：224 输入分辨率、horizon 10、40k checkpoint。报告汇总其四套件为 0.99/0.995/0.98/0.93、平均 97.4%，但 raw checkpoint 和 protocol tuple 待补。不要把 run id 讲成当前 Qwen checkpoint；要解释它对应的配置语义和证据等级。
LIBERO 97.4% 如何解释？这是项目报告记录的 archive-summary-only：goal/object/spatial/libero_10 为 0.99/0.995/0.98/0.93，平均 97.4%。由于 checkpoint、trial/seed、init state、episode records 未闭合，我不把它与 official OpenPI pi05_libero 96.85 做强比较。这是仿真 benchmark 汇总，不等于 current formal Qwen 结果，也不等于真实机器人泛化。
97.4% 是当前 Qwen formal reproduction 直接训练出来的吗？我会谨慎说：97.4% 来自归档中的 strongest LIBERO eval evidence；当前 Metax/Qwen formal reproduction 的价值是恢复历史训练语义、数据/动作契约和 checkpoint 保存路径，证明这条路线可以被可审计地重建。两者相关，但不能把 LoRA formal 训练线直接说成原 checkpoint 的完整来源。这句是边界防线。不要为了显得“更强”而说成完整原样复刻同一 checkpoint。
为什么不和内部 run 比？内部 run 不适合作为简历外部比较。面试里只和公开官方 baseline 对齐，保证口径可解释、可验证。避免泄露或使用不可解释内部信息。
LIBERO 高分能证明什么，不能证明什么？能证明在规整仿真协议下动作表示、normalizer、controller 和 rollout 评估闭环有效；不能证明真实机器人上的视觉扰动、延迟、接触和长任务组合泛化。主动给 sim-to-real 边界。
如果 rollout 失败，你如何定位？先看任务文本和图像，再看 action token 是否可解析，decode 后动作尺度和夹爪维度是否异常，再看 normalizer、controller clipping、执行频率和视频里的失败阶段。需要 action_debug、rollout 视频和 controller 日志。
Metax/MACA 迁移的价值在哪里？价值在跨算力栈复原训练和评估 contract：让 Qwen/VLA 训练、checkpoint、日志、eval 在国产 C500/MACA 上可执行、可复查、可比较。不要说硬件带来算法提升。
你做的是迁移复现还是算法创新？主责是迁移复现和训练/eval contract 重建；算法理解体现在动作表示、Qwen 接入、动作统一、normalizer/controller 对齐，而不是宣称发明 FAST 或 OpenPI。贡献边界必须主动说清。
为什么要同时保留 VLM-only？VLA 训练容易让模型过度关注动作输出，VLM-only/MindCube 路线用于保留视觉语言能力和多模态输入处理，避免训练后只会生成动作格式。如果没有完整指标，不要声称通用能力提升。
真实机器人上最担心什么？视觉扰动、相机标定、控制延迟、接触摩擦、夹爪误差和任务组合复杂度。这些都不是 LIBERO 完全覆盖的。后续要补扰动评估或真实机器人闭环。
你个人贡献怎么概括？我负责把历史 OpenPI/OpenPiVLA run 迁移到 Metax：恢复 run contract，接入 Qwen3-VL/LoRA，统一动作输出口径，搭建三条训练路径，并完成 LIBERO rollout 评估复现。不要认领上游 NVIDIA 代码和 FAST 方法原创。

连续控制动作为什么可以被离散语言 token 表示？ 关键不是把连续动作“翻译成文字”，而是把一段 action window 变成可由自回归模型预测的离散序列。FAST 先对连续动作做 normalization 和 DCT，把时间相关的动作压到频域系数，再量化/BPE 成 token；推理时 decode、IDCT、反归一化回连续控制量。这样 VLA 的动作建模就变成多模态序列预测问题。 不要说 token 不损失精度；量化和频域截断一定有误差。 FAST tokenizer 代码、action chunk 维度、encode/decode roundtrip 检查。
token 化损失精度怎么办？ 误差主要来自 normalization、DCT 系数截断、量化和 decode。控制上不是一次性开环执行整段预测，而是用 action window/chunk 执行一小段后重新观测，再预测下一段。短 execution window 可以降低累积误差，但推理成本更高；长 window 更流畅，但更依赖开环预测。 不要把 LIBERO 高分当成真实机器人精度证明；它只证明规整仿真协议下有效。 horizon/replan_steps 配置、action norm 分布、rollout 视频。
horizon 和 action chunk 怎么影响闭环控制？ horizon 决定模型一次预测多远的未来动作，chunk/execution window 决定控制器实际执行多少步。horizon 太短，模型看不到跨阶段意图；太长，后半段容易被新观测推翻。execution window 越短，闭环纠偏越强；越长，延迟和算力压力小但失败累积更明显。 不要只背数字，要讲 trade-off 和失败模式。 LIBERO 成功/失败任务、不同 horizon 或 replan_steps 对照。
你到底做了模型创新，还是迁移复现？ 我会清楚分边界：FAST/OpenPI 的核心方法和原 NVIDIA 侧历史实现不是我发明的。我做的是在 Metax/MACA 上把这条路线复原成可训练、可评估的 pipeline，包括 Qwen3-VL/LoRA 接入、三条训练路径搭建、动作输出口径统一、训练保存与 LIBERO eval 适配。我的算法理解体现在动作 contract、normalizer/controller 和 eval protocol 的复原，而不是冒充上游原创。 不要说“我改了整个 VLA 架构”。 recipes.py、formal_train.py、train 脚本、Metax run 报告。
Qwen 接入有什么技术含量？是不是换 backbone？ 不是只改一个模型名。VLA 接入 Qwen 要处理 chat template、视觉输入、assistant-side action token/JSON 监督、LoRA target、loss mask、保存/加载格式，以及 eval 时如何把模型输出解析回动作。面试里我会把它讲得克制：这是为了让历史 OpenPI 训练意图迁移到当前 Qwen3-VL 和 Metax 资源上的可执行路径。 不要把 assistant-side JSON 路径说成原 FAST/action expert 的完全等价复刻。 Qwen recipe、loss mask、输出解析脚本、失败样例。

如果动作输出格式正确但 rollout 失败，你怎么定位？ 我会按闭环分层：先看语言/视觉输入是否对应任务，再看 action token 是否可 parse；接着看 decode 后 action scale、normalizer 和夹爪维度；然后看 controller clipping、执行频率和环境 reset；最后看视频里是定位错、接触错还是长时序累积。格式正确只是第一关，不能代表控制正确。 不要把所有失败归因到 eval 环境，除非有 trace 证据。 action debug、rollout 视频、normalizer 对齐表、controller 日志。
国产化适配怎么讲才不像工程杂活？ 我会把它放在“训练迁移与可复现实验”里讲：大 GPU 资源主要在沐曦 C500/MACA 上，因此要让 VLA/WAM/UWM 的训练、保存、eval 和数值协议在国产算力栈上成立。它的价值不是硬件名本身，而是把模型输入输出、checkpoint、normalizer 和评估协议迁移后仍保持可比。 不要单独堆硬件适配细节，也不要说国产卡本身带来算法提升。 MACA run contract、训练日志、eval 对齐报告。

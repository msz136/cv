问题（Question）

面试官会问：“UWM 的评估协议为什么是核心难点？不同 init、warmup、normalizer、checkpoint、rollout 数真的会让结果不可比吗？失败轨迹说明了什么训练分布缺口？”

短答案

可直接口述：UWM 项目的价值不只是训练了一个 checkpoint，而是把官方训练到评估的闭环协议迁移并固定下来。机器人策略评估对初始状态、动作归一化、warmup、checkpoint、rollout 数非常敏感；这些因素任何一个变化，成功率都可能不是模型能力差异，而是协议差异。所以 strict protocol 的意义是保证结果可比：同一 checkpoint 来源、同一 normalizer、同一 init、同一 warmup、每任务 50 rollouts。当前 5-task average 是 74.4% (186/250)，任务间 0.62-0.88；失败轨迹显示 soup_cheese 的夹取精度和长时序恢复是主要缺口，说明世界模型 rollout 分支还需要覆盖更细粒度接触和失败恢复分布。

为什么 Strict Protocol 重要

协议因素如果不固定会怎样本项目处理面试表达
Init state 初始物体位置不同，任务难度完全变化。 pruned_init 保证任务起点可比。
Warmup 一开始机器人状态未稳定，动作输出可能被非策略因素影响。 5-step zero-action warmup 隔离初始化瞬态影响。
Normalizer 动作尺度错会造成系统性过冲或动作幅度不足。 统一动作归一化和 checkpoint 配套 normalizer 这是策略评估最常见的隐藏坑。
Checkpoint 预训练、finetune、任务 checkpoint 混用会让结果不可解释。 LIBERO-90 checkpoint → 5 个 LIBERO-10 下游任务 finetune 说明训练来源和评估对象。
Rollout 数 低 episode 数方差大，容易误报。 50 rollouts/task，共 250 episodes 让 success rate 有基本统计稳定性。

成功率估计可以写成：

\[ \hat{p}_{task} = \frac{1}{N}\sum_{i=1}^{N}\mathbf{1}[\mathrm{success}_i], \quad N=50 \]

其中 \(\hat{p}_{task}\) 是单任务成功率，\(N=50\) 是每个任务 rollout 数。实现映射上，简历中写的是 5-task average 74.4% (186/250)，说明总成功次数来自固定 5 个任务、每任务 50 次，而不是宽松 reset-style 对照。

失败轨迹说明了什么训练分布缺口

失败类型现象可能训练分布缺口后续方向
soup_cheese 夹取精度 接触点、抓取姿态或对象定位略偏导致失败。 细粒度接触、对象几何、视觉定位误差覆盖不足。 增加接触敏感任务、局部视觉扰动、失败恢复样本。
长时序恢复 早期小误差在后续步骤累积，策略无法回到可成功状态。 训练数据偏专家轨迹，缺少 off-distribution recovery。 世界模型 rollout 分支加入扰动状态和恢复监督。
动作尺度偏差 动作过冲或不足。 normalizer 或任务间动作分布差异。 检查 per-task normalizer 和 action denorm。

5. 2-3 分钟口述稿

UWM 这个项目我主要想讲评估协议，因为机器人策略复现里很多结果差异不是模型本身，而是 init、warmup、normalizer、checkpoint 和 rollout 数带来的协议差异。我在沐曦 C500/MACA 上迁移 UWM 官方 LIBERO 训练与评估流程，从 LIBERO-90 checkpoint finetune 到 5 个 LIBERO-10 下游任务，并固定动作归一化、初始化状态和评估脚本。评估上使用 pruned_init、5-step zero-action warmup、50 rollouts/task 的 strict closed-loop 协议，得到 5-task average 74.4% (186/250)，任务间成功率 0.62-0.88。这个结果不包装成超过官方，而是用来分析失败分布：soup_cheese 的夹取精度和长时序恢复是主要误差来源，说明世界模型 rollout 分支需要补更细粒度接触、扰动状态和失败恢复样本。这个项目体现的是我对评估可比性和失败归因的控制，而不只是跑了一个 benchmark。

追问树与回答分层

问题危险回答可过回答强回答
“评估协议有什么技术含量？” 就是按官方跑。 协议会影响结果。 机器人评估中 init、normalizer、warmup、checkpoint、rollout 数都会改变分布；固定协议是做可比失败归因的前提。
“为什么不写更高的 reset-style 结果？” 那个也可以写。 不够严格。 reset-style 和 strict closed-loop 不是同一协议，写进去会破坏可比性；宁愿写低但严格的结果。
“失败轨迹有什么价值？” 用来看看哪里失败。 帮助定位问题。 把失败从单个数字拆成训练分布缺口：接触精度、长时序恢复、off-distribution state，指导下一轮数据和 world rollout 设计。
